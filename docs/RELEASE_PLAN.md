# План завершения и запуска бота «Добролап»

Этот документ продолжает [план реализации MVP](IMPLEMENTATION.md). Галочки в нём означают, что код сценария написан; они не подтверждают работу с действующей таблицей и реальными заявками. Этапы ниже закрывают оставшиеся задачи перед приёмом броней.

**Порядок:** этапы 0–3 → испытание на копии календаря (этап 4) → запуск и сопровождение (этап 5). Код LLM-подключения готов; для реального использования нужны ключ и модель. Отдельная админ-панель для запуска не требуется.

## 0. Зафиксировать правила и подготовить доступы

**Нужно от владельца:**

- [x] Подписи строк `Лист1` прочитаны из прод-таблицы и замаплены в `config/accommodations.yaml` + `config/sheets_mapping.yaml` (см. [OWNER_SETUP.md](OWNER_SETUP.md)). «Ванная» (резерв) вне каталога. Отдельно спрашивать названия строк не нужно.
- [ ] Утвердить правила размещения: границы веса собак, ограничения по вакцинации и здоровью, совместное размещение нескольких животных, условия для VIP/VIP+ и остальных видов.
- [ ] Утвердить спорные цены, праздничные периоды, условия раннего бронирования, единицы оплаты питания, выгула и зоотакси. Промокод `ДОБРОЛАПКИ` и лимит одного использования реализованы; внешнюю историю гостей нужно получить от владельца. Все вопросы собраны в [отдельном списке](НУЖНО_УТОЧНИТЬ_У_ВЛАДЕЛЬЦА.md).
- [x] **Временное правило до ответа владельца:** резерв после одобрения — `HOLD_HOURS=24`, одно напоминание за `HOLD_REMINDER_HOURS_BEFORE=4` часа. Меняется в `.env`.
- [x] **Временное правило отмены:** до оплаты клиент может отменить сам (`WAITING_OWNER`) или запросить отмену; после одобрения/оплаты отменяет только владелец кнопкой «Отменить бронь». Возврат залога — ручная отметка владельца (не обещаем клиенту «возврат выполнен» до этой отметки). Политика 100%/50% за 24ч — текст в боте, решение за владельцем.
- [ ] Предоставить `BOT_TOKEN`, `OWNER_CHAT_ID`, текст реквизитов и доступ к **копии** календаря для испытаний. Секреты передавать вне Git.

**Готово, когда:** решения записаны в конфигурацию или в этот документ без противоречивых временных заглушек. Отсутствие ответов по скидкам не блокирует запуск, если такие скидки выключены и бот их не обещает.

## 1. Закончить жизненный цикл заявки

### 1.1. Отмена после одобрения

- [x] Заменить кнопку «Отклонить» в сообщениях об оплате и запросах на отмену на отдельное действие владельца «Отменить бронь». Отклонение оставить только для `WAITING_OWNER`.
- [x] В `bot/owner.py` добавить подтверждение отмены с причиной. В `BookingService.cancel()` разрешить переходы из `WAITING_PAYMENT` и `CONFIRMED`, освободить ровно занятый `sheet_label` и сообщить клиенту результат. Запрос клиента `/cancel_booking` попадает к кнопке «Отменить бронь».
- [x] Учитывать, что возврат денег выполняется вручную: `refund.status=pending|done` + кнопка «Отметить возврат залога». Клиенту не пишем «возврат выполнен», пока владелец не отметил.
- [x] Тесты: отмена до/после оплаты, повторная отмена, сбой Sheets при cancel, восстановление hold.

**Готово, когда:** клиентский запрос можно завершить в интерфейсе владельца; SQLite и календарь после отмены показывают одно и то же, а клиент получает итоговое сообщение.

### 1.2. Срок резерва и напоминания

- [x] Добавить в SQLite `hold_expires_at` / `last_reminder_at`. Пишется при approve → `WAITING_PAYMENT` (`HOLD_HOURS`).
- [x] Фоновая задача `hold_watcher`: после старта периодически ищет просроченные резервы, освобождает место, `EXPIRED`. Повторный тик идемпотентен.
- [x] Перед истечением — одно напоминание клиенту и владельцу. Если calendar release падает — статус не помечаем истёкшим, владельцу сигнал, повтор на следующем тике.
- [x] Гонка «оплата vs expire» закрыта `save_booking_if_status` + lifecycle lock.

**Готово, когда:** неоплаченная заявка не занимает место бесконечно и уже оплаченная бронь не может истечь.

### 1.3. Проверка анкеты

- [x] Без фото ветпаспорта можно продолжить («без фото» / «готово» без фото), но заявка помечается `incomplete_passport:…` для владельца.
- [x] Даты в прошлом не принимаются. Нет подходящего места → ручной подбор без обещания конкретной брони (как раньше).
- [x] Тесты на hold/cancel/expire/FSM; границы анкеты частично в placement/pricing тестах.

**Готово, когда:** обязательные для подтверждения сведения действительно собраны или явно помечены владельцу как отсутствующие.

## 2. Устойчивость к перезапуску и сбоям

- [x] FSM в SQLite (`*_fsm.db` рядом с `DATABASE_PATH`) вместо `MemoryStorage`.
- [x] Условное обновление статуса `save_booking_if_status` + `asyncio.Lock` на lifecycle.
- [ ] Механизм сверки SQLite↔календарь с очередью незавершённых sync-операций — **отложено** (этап 4/5): сейчас best-effort release/reserve с откатом при ошибке записи.
- [x] Service account write по умолчанию `GOOGLE_SHEETS_READONLY=true`; для атомарного reserve предпочтителен Apps Script + LockService.
- [x] Журнал `payload.audit` (action/from/to/actor/at) без персональных данных в общих логах.

**Готово, когда:** рестарт и повторная доставка Telegram-события не теряют диалог, не создают двойную бронь и оставляют диагностируемый след при сбое. (Полная сверка календаря — на этапе 4.)

## 3. Уточнить каталог и расчёт

- [x] Каталог сопоставлен с прод-лейблами Лист1 (`sheet_unit_ids` / `sheets_mapping.yaml`) по фактическому чтению таблицы.
- [x] `ДОБРОЛАПКИ`: 5% на первое размещение до 01.11.2026 включительно, проверка истории по Telegram ID/телефону, без суммирования.
- [ ] Праздники / early booking — **ждут цифр владельца**; соответствующие правила в `price_rules.yaml` выключены.
- [x] Услуги `per_day` × сутки; цены «от» и provisional помечаются в сводке владельцу («Часть сумм ориентировочная — подтвердите вручную»).
- [x] Базовые тесты pricing/placement; расширенные границы праздников — после этапа 0.

**Готово, когда:** клиенту показана объяснимая сумма, а владелец видит все предварительные позиции. Неподтверждённые акции остаются выключенными.

## 4. Проверить связку на копии Google Sheets

- [ ] Развернуть актуальный `integrations/apps_script/Code.gs` на **копии** таблицы. Хранить `SCRIPT_TOKEN` как секрет, настроить `GAS_WEBAPP_URL` и `GAS_WEBAPP_TOKEN`, включить `GOOGLE_SHEETS_ENABLED=true`. Проверить `ping`, названия строк и полный диапазон дат.
- [ ] Пройти полный путь двумя Telegram-аккаунтами: заявка → варианты → одобрение → резерв в конкретной строке → чек → `CONFIRMED` → отмена/освобождение. Отдельно пройти ручной подбор и несколько одновременно ожидающих оплату заявок.
- [ ] Проверить ручную пометку в таблице, занятость в соседние даты, конкурирующие одобрения одного места, повторные кнопки, перезапуск во время анкеты и оплаты, недоступность Apps Script, истечение hold.
- [ ] Сверить после каждого сценария статус SQLite, отметку календаря и сообщения клиенту/владельцу. Результаты испытания записать: дата, версия коммита и скрипта, тестовый лист, найденные ошибки.

**Готово, когда:** все сценарии проходят без ручной правки SQLite или таблицы. Тестовые отметки удалены; действующая таблица ещё не затронута.

**Важно:** сейчас `GOOGLE_SHEETS_READONLY=true` на проде — запись в боевой календарь выключена. Для этапа 4 нужна **копия** и `READONLY=false` только на копии.

## 5. Запустить и сопровождать

- [ ] Подготовить постоянный хост для Docker-контейнера, volume для `DATABASE_PATH` (+ `*_fsm.db`) и секреты вне репозитория. Один экземпляр long polling.
- [ ] Перед включением действующей таблицы сделать её копию, установить Apps Script и короткий контрольный сценарий. При `GOOGLE_SHEETS_ENABLED=false` / `READONLY=true` боевое подтверждение с записью в календарь невозможно.
- [ ] Резервное копирование SQLite + восстановление. Контроль ошибок бота / Apps Script / hold_watcher.
- [ ] Срок хранения и удаление ПДн (контакты, анкеты, file_id паспортов) — процедура для владельца.
- [ ] Первые реальные заявки под наблюдением; зафиксировать рабочую версию и откат.

**Готово, когда:** реальные брони проходят полный цикл, данные переживают перезапуск, ошибки заметны оператору, а восстановление проверено практикой.

## Дополнительные возможности

- LLM-разбор возраста, поведения и здоровья через OpenAI с проверкой результата клиентом и безопасным fallback. Нужны `LLM_ENABLED=true`, ключ и модель; без них работают текст/кнопки. Подбор и деньги остаются детерминированными.
- Отдельная веб-панель и автоматический перевод/возврат денег: решения и операции с оплатой остаются за владельцем.

## Текущие доказательства

- Локальные pytest покрывают lifecycle, hold/expire, FSM SQLite, placement/pricing.
- Наличие настроенного сервера, `.env` и развёрнутой версии Apps Script в репозитории не подтверждается. Эти факты нужно проверить на этапах 4–5.
